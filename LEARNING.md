# Learning Log

Ferguson is also a learning project — I'm picking up Go for the first time by building a real application with it, pair-programming with Claude Code. This file tracks what I've actually learned, day by day, as a record of the process (not just the output).

**How the pairing works:** for core files (`main.go`, `model.go`), Claude explains the concept and shape first, then I write the code myself — Claude points out bugs by category and lets me find the fix rather than handing me the answer. Boilerplate (HTTP clients, struct definitions, styling) gets generated directly to keep momentum. Full methodology is in `CLAUDE.md`.

## Day 1 — Go fundamentals, Bubbletea's architecture
Started with zero Go experience — didn't know how to write a function. Built a working `Model`/`Update`/`View` loop (The Elm Architecture) from scratch, wired to a CLI entry point with flag parsing. Concepts covered: structs and methods (Go's answer to classes), receivers, pointers, multi-value returns, JSON struct tags, Go's package/export system, error-handling idioms.

## Day 2 — HTTP, JSON parsing, async patterns
Built a full HTTP client against the live Fantasy Premier League API, including nested JSON unmarshaling (an outer "envelope" struct wrapping a list of player structs — matching the real API response shape rather than assuming a flat structure). Wired an async fetch into the app using Bubbletea's `Cmd`/`Msg` pattern — functions that return functions (closures), and a custom message type to carry fetch results back into the update loop without blocking the UI.

## Day 3 — Styling, data transformation
Lip Gloss styling (colors, borders, panes) matching a Bloomberg Terminal-style visual spec. Wrote a data-transformation function that converts raw API structs into display-ready rows (loops, slices, type conversion).

## Day 4 — Second data pipeline, JSON shape-matching, multi-pane layout
Built a full second data pipeline (fixtures) end-to-end, mirroring the squad pipeline's shape: a new struct matched to a live API response, an HTTP client, a multi-stage transform pipeline (filter, group by key into a map, trim), a formatter, and full `Model`/`Update`/`View` wiring using `tea.Batch` to run two async fetches concurrently from `Init`. Went deep on how `encoding/json` actually decides what matches what — a hard category check (JSON object/array/string vs. Go struct/slice/string) followed by lenient, best-effort field-by-field tag matching — and used that understanding to correctly determine, by checking the live API response rather than assuming, that this endpoint's flat-array shape needed no wrapper struct (unlike the squad endpoint's object-wrapped shape). Learned `lipgloss.JoinHorizontal` for laying out multiple panes side by side. Diagnosed and fixed a real pipeline-ordering bug independently, using an isolation test (temporarily rendering one pane alone) to separate a data problem from a layout problem.

## Day 5 — Cross-package data flow, difficulty color-coding, variable scope
Added color-coded fixture difficulty ratings (5 distinct shades) to the fixtures pane, which required designing around a real architectural constraint: styling logic lives in one package while the data-formatting logic lives in another, and Go doesn't allow importing the entry-point package from a library package. Solved by pre-rendering styled output in the entry-point package and passing it down as plain data — a pattern that generalizes to any case where presentation and data-transformation logic need to stay in separate packages. Also added a loading state to the UI, which involved a genuine Go variable-scoping lesson: values declared inside an `if`/`else` block don't exist outside it, so shared state needs to be declared once, outside, and assigned (not re-declared) inside each branch.

## Day 6 — Two AI providers, prompt engineering, and Bubbletea's timer pattern
Built a full AI integration layer with two independent, from-scratch clients: Google Gemini (API key as a URL query parameter, deeply nested request/response JSON) and Groq (API key in an `Authorization: Bearer` header instead, which meant switching from the one-line `http.Post` shortcut to the longer `http.NewRequest` + `http.Client.Do` pattern, since only the latter lets you attach custom headers before sending). Learned to compose small functions into larger ones — each provider's marshal → send → unmarshal → extract steps got chained into a single "get me a reply" function, and those two got wrapped in a fallback function that tries one provider and only calls the second if the first errors, a real redundancy pattern.

Wrote the actual Ferguson's Verdict prompt myself: a persona block, rules for FPL squad composition and captain/formation mechanics, and a data section describing the live squad/fixture data that gets programmatically appended to it at request time — prompt engineering as its own real skill, separate from the Go plumbing around it.

The hardest new concept this day was `tea.Tick`, Bubbletea's timer mechanism, used to build a typewriter-style reveal for the AI's reply one character at a time. Understanding it required first getting a clear model of Bubbletea's concurrency: `Update` and `View` always run on one single main goroutine, one at a time, and the only thing that ever runs concurrently is a `Cmd`'s inner function — which is also why a `Cmd` can never touch `Model` directly, only report back via a message. Once that clicked, the tick mechanism itself was just: a message type, a function that waits and produces that message, and an `Update` case that reveals a bit more text and reschedules the next tick until the string runs out. Also hit a real runtime panic from incrementing the reveal counter by more than one character per tick without capping it at the string's actual length — a good concrete lesson in off-by-N slice-bounds errors, not just off-by-one.

## Day 7 — Selection-driven UI, and debugging past a generic error message

Built the player detail pane: selecting a row in the squad table and hitting enter now swaps the fixtures pane for that player's own info and upcoming fixtures, esc reverts it. This meant going back through `model.go`'s core mechanics until they actually stuck — the `cmd`/`cmds` pattern, why `Update` returns `(Model, Cmd)`, and Go's type-switch rule that a type switch's `msg := msg.(type)` creates a separately-typed version of the variable per case, not one variable being silently overwritten (a real language-level special case, not inferred from ordinary variable scoping). Once that was solid, wiring the detail pane was mostly about composition: reusing `FindUpcomingMatches`, `FixturesForClub`, and `FirstFive` — three functions already written for the main fixtures pane — chained together in a new combination for a single selected player, instead of writing new logic from scratch. Caught two real bugs in my own code along the way: an infinite loop from a missing loop-increment, and a swapped home/away opponent lookup that would've shown a player's own club as their opponent.

Also spent real time proofreading my own code comments against what the functions actually do, not just what I intended them to do — found comments claiming a function returned "the first five" when it actually returned everything unfiltered, and a club-ID argument position stated backwards from the real signature. Comments describing what a function *itself* guarantees, versus what happens to be true because of how it's currently called elsewhere, turned out to be a real, useful distinction.

Hit a "both providers failed" error that looked identical to a past incident assumed to be transient — this time, traced it properly instead of guessing, by testing the Groq/Gemini endpoints directly with `curl`/`Invoke-RestMethod` (bypassing the app's own error handling) and adding temporary raw-response logging around both provider calls. Turned out to be two unrelated real causes at once: Groq rejected the request for exceeding its account's tokens-per-minute limit (the prompt bundles all ~626 players, well beyond the 8,000 TPM cap), and Gemini was genuinely overloaded on its end (a transient 503). Neither was a code bug — a good lesson that a generic caught-and-rewrapped error message can hide two completely different real causes, and the fix was to go look at the actual raw HTTP response instead of reasoning about it in the abstract.
